## 0. 一句话设计

把数据底座从"能取数"升级为"研究基础设施"：**纵轴是三层宇宙（哪些币能用），横轴是时间墙研究池（什么时间的数据能用），墙在 API 层强制，不是在纪律里约定。** 这样人和 Agent 都无法偷看未来。

## 1. 背景与目标

### 1.1 现状
- 已构建 **40 个认证数据集、约 1.22 亿行**，三层交易宇宙（research ⊇ backtest ⊇ tradeable）已上线（纵轴完成）。
- 三层宇宙回答的是"**某时刻哪些币有资格被研究/回测/交易**"。

### 1.2 缺什么
纵轴只回答了"哪些币"，没回答"**什么时间的数据能被谁看到**"。量化研究最致命的错误是**数据泄露（look-ahead bias）**：回测里用了未来才知道的信息，得到漂亮但虚假的指标。

### 1.3 目标
构建"时间墙研究池"体系（横轴），与三层宇宙正交：
- **池1 开发池（OOF）**：训练、调参、随便试错。
- **池2 反馈池**：输出指标做反馈，用于验证和少量选择。
- **池3 OOS 池**：**进入交易前的最后一道闸门，不给任何反馈**，只默默记录各版本算法能力。
- 数据底座作为**基础设施（服务 / MCP）**同时供研究员与多个 Agent 使用，支撑后续**特征体系**与**模型研究协议**。

## 2. 时间墙为什么是生死线

回测骗人的特点：**不报错，只给你一个漂亮的假数字**。在开发池上把夏普从 1.2 优化到 2.8，若混入一点未来信息，这个 2.8 就是假的；假象进了 OOS，实盘亏钱时你根本不知道原因。

泄露是**隐性的**：格式对、代码能跑、没有任何报错。所以必须靠**制度（严格时间墙）+ 机制（API 层强制）**防，不能靠自觉。

## 3. 业界标准做法（网络检索）

### 3.1 Purged K-Fold + Embargo（López de Prado, *Advances in Financial Machine Learning* 第 7 章）
处理两条泄露通道：
- **标签重叠（label overlap）**：金融标签是"未来 H 天的收益"，训练集末尾的样本其标签窗口会"伸进"测试集 → **Purge（清洗）**：删掉这些样本。
- **序列相关（serial correlation）**：即使标签不重叠，测试集边界附近样本因滑动窗口特征高度相关 → **Embargo（禁运）**：测试集之后再删一小段，长度**至少等于标签周期 H**。

### 3.2 三重屏障法（Triple Barrier，第 3 章）
标签由三面墙决定：止盈（上）、止损（下）、时间（垂直）。它定义了**标签生存期 H**——隔离带长度不是拍脑袋，是从标签定义推出来的。

### 3.3 多重检验校正（Deflated Sharpe Ratio, Bailey & López de Prado）
试了 N 个参数组合，最优夏普天然被抬高。DSR 的输入之一是**试验次数 N**——这正是 OOS"只默默记录版本"的价值：它记录的 N 用来做校正。若 OOS 被反复查看调参，它就退化成池2，统计效力归零。

> 参考：[purgedcv](https://pypi.org/project/purgedcv/0.1.6/) · [purged-cross-validation 论文](https://github.com/eslazarev/purged-cross-validation/blob/main/paper/paper.md) · [Walk-forward 与 Purged CV 对比](https://quant67.com/post/quant/21-walkforward-cv/21-walkforward-cv.html) · [Deflated Sharpe Ratio](https://jonathankinlay.com/2026/09/the-holdout-that-made-the-sharpe-bigger/) · [Backtest overfitting in the ML era](https://www.sciencedirect.com/science/article/abs/pii/S0950705124011110)

## 4. 池划分的第一原则：边界 = f(因子集)，不是全局唯一

**这是对"为什么从 2019 年开始"这个质疑的正面回答。** 从 2019 年开始是错的——那是拿"永续数据最早起点"当基准，而不是从"要研究什么"倒推。

正确做法：**池边界由所选因子集的"可用性交集"决定**。不同研究线（只用现货 vs 含衍生品 vs 含链上）可用的起点完全不同。

> **任何因子在其可用起点之前，在该池内必须被屏蔽（不可用）。** 否则会得到"某因子只在最近 N 天有效"的假象——这是时间墙要防的另一种泄露。

落地：维护一份 `factor_registry`（数据集 → availability_start），查询时自动钳制。

## 5. 池结构：三池 + 两条不可跨越的隔离带

```
├──────────┬────────┬───────────┬─────────┬───────────┬─────────┬─────────┤
│  预热区   │ 池1    │  隔离带1 │  池2    │  隔离带2   │  池3    │ 滚动OOS │
│ (特征预热)│  OOF   │ purge+    │ 反馈池  │ purge+    │  OOS    │ (季度   │
│          │ 开发池  │  embargo  │        │  embargo  │         │  开启)  │
└──────────┴────────┴───────────┴─────────┴───────────┴─────────┴─────────┘
     ↑              ↑                                ↑
  只用于特征      隔离带被"烧掉"，                 永不查看
  预热+标签成熟   两边都不能用
```

### 5.1 隔离带长度怎么算
```
隔离带长度 G = max(标签生存期 H, 数据修订滞后 R)
```
- **H（标签生存期）**：策略最长持有时间。对 4h K 线体系：

| 策略持有期 | 标签 H | 建议隔离带 G |
|---|---|---|
| 1 天（6 根 4h） | 1d | 3 天 |
| 3 天（18 根 4h） | 3d | 7 天 |
| 7 天（42 根 4h） | 7d | **14 天** |

- **R（数据修订滞后）**：若数据源会事后修订历史（CMC 市值、宏观回填），隔离带须覆盖其修订窗口。每个数据集 manifest 需增加 `revision_lag_days` 字段。
- **建议默认 G = 14 天，别省。** 多留几天数据的代价，远小于一次泄露发现不了的代价。

### 5.2 池边界（已定稿：方案 A + universe 回填到 2017-07）

> **决策（2026-10-03 拍板）**：采用方案 A（含衍生品），并**回填 universe_membership 到 2017-07**，使池1 提前到 2018-01，覆盖 2018 大熊市。
>
> **回填可行性（已实测）**：
> - `listing_universe.first_period` 最早 **2017-07**（Binance Vision 归档极限，2017 年 230 个交易对）→ 回填下限 = 2017-07
> - CMC 市值 2013 起、BTC 现货 1h 2017-08-17 起 → 输入数据覆盖 2017-07 无缺口
> - 结论：**universe_membership 可回填到 2017-07**（不能到 2017-01，受 listing 归档限制）

### 6.1 修订泄漏审计结果（2026-10-04 执行 `_audit_revision_leak.py`）

判据：`lag = data_available_at - 事件时间`。lag 稳定 = 当期快照抓取（合法）；lag 随历史深度增大 = 事后抓全量历史并可能已修正（污染）。

| 数据集 | 区间 | lag 中位 | lag 早期 | lag 近期 | 漂移 | 判定 |
|---|---|---|---|---|---|---|
| **cm_asset_daily** | 2009~2026 | 2110d | 4110d | 1585d | +2525d | 🔴 污染 |
| **macro_daily** | 2005~2026 | 3937d | 5917d | 1945d | +3972d | 🔴 污染 |
| **btc_network_daily** | 2009~2026 | 3069d | 4756d | 1614d | +3142d | 🔴 污染 |
| sentiment_fng | 2018~2026 | 0.81d | — | 0.81d | 0 | ✅ 安全 |
| stablecoin_peg | 2018~2026 | 0.04d | 0.04d | 0.04d | 0 | ✅ 安全 |
| stablecoin_supply / flows / dex_volume | — | — | — | — | — | ⚫ 无 `data_available_at` 列，无法 PIT |
| **spot 1h / funding / mark**（核心价格） | — | 0.00~0.04d | — | — | 0 | ✅ 安全 |

**结论与处置**：
1. **核心交易因子（价格、资金费率、OI、mark/index、多空比）PIT 干净**，lag ≤ 1 小时收盘确认 —— 这是研究池的主力，可放心使用。
2. **宏观 (macro_daily)、cm_asset_daily、btc_network_daily 为事后回填的历史**，用它们回测历史等于用了"事后才知道的信息"。**处置：这三个数据集在历史池（池1/反馈）中标记为 `revision_contaminated`，默认屏蔽**；若要使用，须先做"仅保留 lag ≤ 阈值"的近期窗口（如只回看近 2 年），或从现在起每日快照自积累（届时 PIT 才成立）。
3. **stablecoin_supply / flows / dex_volume 缺 `data_available_at`**，无法做 PIT 过滤，同样在池中屏蔽，直至补齐该列。

## 7. OOS 池治理机制（定稿：Agent 盲 + 研究员可读）

> **决策（问题 3，2026-10-03 拍板）**：OOS 不是"没人能看"，而是**角色分级**——
> **模型/算法送进去，Agent 看不了结果；研究人员可以看结果并做最终 go/no-go 决策。**
> "不给反馈"约束的是 **Agent 的自动迭代回路**，不是人的监督权。

### 7.1 角色分级访问（核心机制）

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| **Agent** | 提交模型版本进 OOS；查询提交状态（pending/evaluated） | **读不到任何 OOS 分数/指标**（API 层硬隔离，无参数可绕过） |
| **研究人员** | 读取 OOS 评价结果；做 go/no-go 决策 | 查看行为被全程留痕（见 7.3） |

**为什么人可以看、Agent 不能看**：
- 泄漏的本质是"**看到分数 → 自动回去改 → 再测**"的闭环。Agent 的迭代是自动的、高频的，一旦能读 OOS 分数，它必然把 OOS 当反馈池用，且不留痕迹。
- 研究人员的查看是**低频的、有意识的决策行为**（批准上线 or 打回），且每次查看都留痕、可审计。人的"看结果后让 Agent 改"也会被账本记录为一次新的试验（N+1），无法隐身。

### 7.2 四条铁律
1. **写入一次（write-once）**：每个版本对 OOS 的评价结果只产生一次，记录后不可修改、不可重跑（除非显式作废并记 N+1）。
2. **Agent 盲**：OOS 评价结果对 Agent 角色**物理不可读**；Agent 只能拿到回执（evaluation_id + 状态），拿不到分数。
3. **人员可读、留痕**：研究人员读结果要走单独的**人审通道**（非 MCP 工具），每次查看记入账本（谁、何时、看了哪个版本）。
4. **版本打回即 N+1**：任何版本在 OOS 查看后被拒绝/修改，下一个提交的版本计为新试验——账本累计的 N 是 DSR 校正的输入。

### 7.3 为什么"Agent 不给反馈"是必须的
```
Agent 在 OOS 看到分数低 → 自动回去改参数 → 再测 OOS
        ↓
   OOS 退化成池2（反馈池），统计效力归零，且无人察觉
```
DSR（Deflated Sharpe Ratio）需要真实的试验次数 N。若 Agent 偷偷在 OOS 迭代 50 次，上报夏普必须按 50 次折现，否则是自欺欺人。**Agent 盲是从机制上保证 N 真实**：账本只记录"显式提交的版本数"，Agent 无法在账本外试探 OOS。

> 对研究人员的纪律建议（非强制，但写进协议）：OOS 结果用于**验收**，不用于**调参指导**。"看了 OOS 再改"在统计上等价于多一次试验，账本 N 会如实反映——人员看到的不只是分数，还有自己的行为记录。

## 8. 基础设施化 / MCP 服务：墙在 API 层强制

### 8.1 核心原则
> **时间墙不能靠"约定"，必须靠 API 强制。** 人会犯错，Agent 更会犯错（它只会看到工具返回什么，不拦它一定会去查）。**API 不返回数据，是唯一可靠的防线。**

### 8.2 池作用域（Pool Scope）
```
Agent / 研究员
      ↓
   MCP Server   ← 墙在这里强制
      ↓
┌──────────────────────────────────────────┐
│ 会话启动时绑定 pool_id（不可改）            │
│   query(dataset, instruments, as_of)      │
│     as_of := min(请求 as_of, pool.end)     │  ← 硬钳制
│     instrument ∈ universe(pool.as_of,层)   │  ← 宇宙门控
│     factor 屏蔽: 早于 availability_start    │  ← 因子屏蔽
│   → 永远返回不了池外的数据                  │
└──────────────────────────────────────────┘
      ↓
   L2 Certified（data_available_at PIT 过滤）
```
Agent 传 `as_of="2026-10-01"`，若在池1里，返回的最大日期仍是池1结束日。**参数只能往前调，不能往后调。**

### 8.3 MCP 工具集（Agent 角色）

| 工具 | 作用 | 池限制 |
|---|---|---|
| `list_pools()` | 返回池注册表（起止日、隔离带、状态、因子集） | 全可见 |
| `query(dataset, instruments, interval, as_of)` | 查数据，as_of 钳制到本池末尾 | 自动 |
| `universe(as_of, layer)` | 取三层宇宙，钳制到本池 | 自动 |
| `factor_available(dataset, as_of)` | 查某因子在某时刻是否可用 | 自动 |
| `submit_metrics(pool, run_id, metrics)` | 提交指标（开发/验证反馈） | 池1/池2 允许；**池3 拒绝** |
| `submit_oos_candidate(run_id, code_hash, artifact_uri)` | 把模型版本送进 OOS 评估 | 仅池3；返回回执 evaluation_id |
| `oos_status(run_id)` | 查版本在 OOS 的评估状态 | 只返回 pending/evaluated，**不返回分数** |
| `eval_count(run_id)` | 返回该版本累计评估次数 N（供 DSR） | 全可见 |

**OOS 评价结果不在 MCP 工具集中**——Agent 角色没有任何工具能读到 OOS 分数。

### 8.4 人审通道（研究人员角色，非 MCP）

| 通道 | 作用 | 约束 |
|---|---|---|
| `oos_result_read(run_id)` | 研究人员读取某版本的 OOS 评价全文 | **每次读取写账本**（人、时间、版本） |
| `oos_verdict(run_id, accept\|reject, note)` | 记录 go/no-go 决策 | reject 后下一版本计 N+1 |

人审通道与 MCP 服务**物理分离**（不同端口/不同鉴权），Agent 的 API 凭证在人审通道上无效。

## 11. 术语

| 术语 | 含义 |
|---|---|
| 纵轴（三层宇宙） | research ⊇ backtest ⊇ tradeable，回答"哪些币能用" |
| 横轴（时间墙研究池） | OOF / 反馈池 / OOS，回答"什么时间的数据能用" |
| Purge（清洗） | 删掉标签窗口伸进下一池的训练样本 |
| Embargo（禁运） | 下一池之后删一小段，防序列相关 |
| 隔离带 | 两池之间被"烧掉"的时间，长度 = max(H, R) |
| H（标签生存期） | 三重屏障时间墙决定的最长持有时间 |
| R（修订滞后） | 数据源事后修订历史的窗口 |
| DSR | Deflated Sharpe Ratio，按试验次数折现的夏普 |
| 幸存时段偏差 | 因子只在最近 N 天存在，误以为长期有效 |
