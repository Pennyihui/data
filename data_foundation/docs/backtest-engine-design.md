---

## 1. 要解决的问题

模型研究协议层目前是空的：从特征到"这个模型能不能赚钱"之间没有一条可验证的链路。

回测引擎是这条链路的最后一环，也是**唯一能把泄漏风险暴露出来**的地方。如果回测里"用 T 根收盘价成交"能跑出漂亮收益，那说明信号和成交之间偷看了未来。

**所以本引擎的第一职责不是算收益，是让泄漏在结构上不可能发生。**

---

## 2. 三条设计原则（借鉴 NautilusTrader）

### 原则1：事件流严格按时间戳排序

所有事件（bar / 目标仓位 / 成交）进同一条时间序列，按 `(ts, seq)` 严格排序后逐个派发。同一时刻内用单调递增的 `seq` 保证确定性。

> Nautilus 的做法：事件驱动 + 严格排序 → 相同输入逐位相同输出。我们继承这一点，见 §7 确定性测试。

### 原则2：回测与实盘同一套代码路径

策略（Strategy）代码**不知道**自己跑在回测还是实盘：它只订阅数据事件、输出目标仓位。换数据源就是换环境，不是换逻辑。

> 这一条决定了引擎的接口形状：`BacktestEngine` 和将来的 `LiveEngine` 共用 `Strategy` / `RiskEngine` / `ExecutionEngine` 三个组件。

### 原则3：时序是结构性的，不是靠自觉

**这是与"自己写回测脚本"最本质的区别。** 防泄漏不靠"记得别用未来数据"的纪律，靠引擎物理上做不到：

| 泄漏类型 | 结构性保障 |
|---|---|
| 用未来 bar 的数据 | Strategy 收到的事件流在物理上只有当前及之前 |
| 用当根收盘价成交 | ExecutionEngine 在**下一根 bar** 才成交，且用下一根的开盘价 |
| 用未来的成分股 | 候选池来自**逐日 PIT 宇宙快照**（universe_membership） |
| 改了非 PIT 数据源 | DataEngine 只接受认证层数据，附 `data_available_at` |

## 3. 架构

```
                          ┌──────────── 事件流 (按 ts 严格排序) ────────────┐
                          ↓                                              ↓
   PIT 认证数据 → [DataEngine] → [Strategy] → [目标仓位] → [RiskEngine] → [ExecutionEngine] → [成交/Fill]
   (44 数据集)      发 BarEvent        发 OrderIntent      仓位约束          下一根 bar 成交      发 FillEvent
                          ↑                                                                              ↓
                          └────────────────── 同一套组件，实盘复用 ──────────────────────────────────  [Portfolio/净值]
```

四个组件的职责边界：

| 组件 | 输入 | 输出 | 不负责 |
|---|---|---|---|
| `DataEngine` | PIT 认证面板 + 宇宙快照 | `BarEvent` 流 | 不知道策略 |
| `Strategy` | `BarEvent`（只含当前及历史） | `OrderIntent`（目标仓位） | 不知道成本、不知道撮合 |
| `RiskEngine` | `OrderIntent` | 修正后的 `OrderIntent` | 不算 alpha |
| `ExecutionEngine` | `OrderIntent` + 下一根 bar | `FillEvent` + 成本 | 不决定买什么 |
| `Portfolio` | `FillEvent` | 持仓 / 净值 / 绩效 | 不做决策 |

## 4. 事件模型

```python
@dataclass(frozen=True)   # frozen = 不可变, 事件一旦发出就不会被改
class BarEvent:
    ts: pd.Timestamp       # bar 收盘时刻 (= open_time + interval - 1s)
    assets: tuple[str,...] # 该时刻的资产 (来自当日宇宙快照)
    open: np.ndarray       # 下一根 bar 的开盘价? -> 见 §5 成交时点
    ...
```

**关键字段：`data_available_at`。** 每个 bar 携带它自己何时可知。DataEngine 在派发前检查 `data_available_at <= 当前决策时点`，不满足就**不派发**——这是最后一道 PIT 闸门。

事件顺序（同一 ts 内）：
```
seq 0: BarEvent(T)            # 数据可见
seq 1: OrderIntent(T)         # 策略基于 T 的数据下目标仓位
seq 2: ExecutionEngine 处理   # 但成交发生在 T+1
```

## 5. 成交时点约定（最关键的设计决定）

**信号在 T 根 bar 收盘时产生，成交发生在 T+1 根 bar 的开盘。**

```
T 根 bar 收盘 (含 T 的全部信息)
    ↓ Strategy 计算目标仓位
T+1 根 bar 开盘 ← 成交价 = open(T+1) × (1 ± 滑点)
    ↓ 持仓开始承担 T+1 的盈亏
```

**为什么不能用 T 的收盘价**：策略在 T 收盘时才算出信号，成交发生在同一时刻需要假设"你在看到收盘价的同一瞬间还能按这个价成交"——现实中做不到。

**为什么不用 T+1 收盘价**：会乐观。更真实的是 T+1 开盘。

> 这个约定写死在引擎里，Strategy 无法覆盖 —— 如果允许覆盖，就等于把泄漏的口子留在配置里。

## 6. 成本模型

```
成交价 = 下一根 bar 开盘价 × (1 ± 滑点bps/10000)
成本   = |Δ权重| × (手续费率 + 滑点)
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `maker_fee` | 0.02% | 挂单 |
| `taker_fee` | 0.05% | 吃单（我们的假设：策略在 T+1 开盘吃单） |
| `slippage_bps` | 5 bps | 单边滑点 |

成本是"换手 × 费率"，而不是拍一个净值折扣 —— 换手率本身就是因子门槛的指标之一（决策 10），要能独立拆出来看。

---

## 7. 确定性与可测试性

引擎必须满足：**相同输入 → 逐位相同输出**。

保障手段：
1. 事件严格按 `(ts, seq)` 排序
2. 资产顺序用排序后的 tuple（不依赖 dict 迭代顺序）
3. 浮点累加顺序固定（净值按时间顺序累加，不用并行归约）

**测试**：
- 跑两遍，净值逐位相同
- 手续费/滑点设为 0 时，净值应等于手工计算的结果（可核对）
- 构造一个"作弊策略"（试图偷看下一根 bar），引擎应该**物理上喂不到它**

## 8. 与既有体系的关系

| | 复用 |
|---|---|
| 数据 | `data_foundation.reader` 读认证层；`universe_membership` 逐日 PIT 宇宙 |
| 特征 | `features.FeatureEngine` 产出的信号面板（作为 Strategy 的输入之一） |
| 时间墙 | `PoolScope` 决定回测窗口；引擎不做二次钳制 |

**引擎不重新实现**：取数、特征、PIT 校验都用现成的。它只做"事件流 + 成交 + 成本 + 净值"。

---

## 9. 不做什么（明确边界）

- **不做 tick / L2 盘口 / 队列位置**（我们没有数据；需要时用 hftbacktest）
- **不做订单簿撮合**（bar 级用开盘价 + 滑点近似）
- **不做优化器**（仓位映射先固定，权重优化属模型协议）
- **不做多策略组合的资金分配**（单策略）

## 10. 实现顺序

1. 事件模型 + 总线（严格排序、确定性）—— 先单独测
2. `DataEngine`（PIT 面板 → BarEvent 流 + 逐日宇宙）
3. `ExecutionEngine`（T+1 成交 + 成本）—— 先用固定目标仓位测
4. `Portfolio`（净值 + 绩效）
5. `RiskEngine`（仓位约束）
6. `Strategy` 基类 + 一个示例策略
7. 端到端测试
